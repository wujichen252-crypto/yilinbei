# 数据库迁移审计报告

**对象**：`apps/core/migrations/` 下的全部迁移文件
**目标**：查清这些迁移建了哪些表、表之间如何关联、各表存放什么数据，并指出风险
**日期**：2026-09-22
**结论摘要**：迁移完整复制了原 Laravel 的 18 张业务表，但**没有复制任何外键**（全库仅 1 个且已关闭约束）。表间关系全部降级为"裸整数"，由应用代码手工拼接。存在 1 项会阻断上线的缺陷和 3 项数据正确性缺陷，详见第五节。

---

## 一、审计范围与方法

审计对象是仓库内的 Django 迁移文件，**不是**生产库。方法如下：

1. 通读 4 个迁移文件与 `apps/core/models.py`；
2. 通过 Django 后端元数据实际计算每个字段的物理列类型（`field.db_type(connection)`），而非依赖文档描述；
3. 用 `grep` 穷举 `ForeignKey/OneToOne/ManyToMany` 声明，确认外键数量；
4. 反向追踪 `apps/api/views.py`、`apps/core/services.py`、`apps/api/export_services.py` 中对每个 `*_id` 列的读写点，还原真实关系语义；
5. 核对仓库内既有文档（`DATABASE_MAPPING.md`、`MIGRATION_GAPS.md` 等）与实际代码是否一致。

> 本次审计为只读操作，未修改任何文件，未连接任何数据库。

## 二、迁移文件清单

| 文件 | 实际作用 | 是否有真实 DDL 变更 |
| --- | --- | --- |
| `0001_initial.py` | 创建全部 18 张业务表 | 是（CREATE TABLE） |
| `0002_auto_20260916_2008.py` | 改名 3 个索引（Django 名称哈希漂移）；将 `password_resets` 设为 `managed=True` | 是（RENAME INDEX） |
| `0003_auto_20260916_2038.py` | 4 处 JSON 字段与 `user.parent` 的 `AlterField` | **否，全部空转** |

关于 `0003` 为什么是空转：它把 `user.parent` 的目标从 `to="core.user"` 改成 `to=settings.AUTH_USER_MODEL`，而 `settings.AUTH_USER_MODEL` 的值就是 `"core.User"`（见 `django_config/settings.py:81`），二者等价；4 个 JSON 字段的 `AlterField` 前后定义完全相同，是 `makemigrations` 的重复输出。

**注意**：`0004` 不是幂等的"附加"，它是真实的 schema 变更。部署到任何已有数据库时，它会执行 35 条 `ALTER TABLE ... ALTER COLUMN ... SET DEFAULT ' '`。

## 四、关联关系

### 4.1 核心事实：全库没有外键

穷举迁移文件中的 `ForeignKey/OneToOne/ManyToMany`，结果只有一处：

```
0001_initial.py:26   User.parent -> self
                     db_column="parent_id", db_constraint=False
```

`db_constraint=False` 意味着**连这一个外键在数据库层面也不生成约束**。其余所有关系都是普通的 `IntegerField` / `BigIntegerField`。

后果：

- 数据库不提供任何参照完整性，孤儿行、悬空引用可以随便写入；
- 不存在级联删除；
- 所有 JOIN 由应用代码逐个 `filter()` 手工完成。

这是**刻意的移植策略**（原 Laravel 迁移同样没有声明外键），不是疏漏。但它把完整性责任全部转移到了应用层，而应用层并未系统性承担——见第五节。

### 4.2 逻辑关系图

```

  │
  ├─ parent_id ──────> users.id           组织层级（省/市 → 学校）
  │
  ├─ report.user_id ─────────────────────> 报名表归属单位
  │     ├─ report.spectrum ──┐
  │     └─ report.file ──────┴──────────> files.id   (曲谱 / 视频)
  │
  ├─ person.user_id ─────────────────────> 人员归属
```

### 4.3 关系类型归纳

| 关系 | 载体 | 性质 |
| --- | --- | --- |
| 用户自关联层级 | `users.parent_id` | 唯一有 FK 声明者，但无 DB 约束 |

## 五、审计发现

按严重程度分三级。

### 5.1 严重：会阻断上线

#### 缺陷 1｜部署会对已有数据库直接执行建表，且缺少 `--fake-initial`

`deploy/deploy.sh:114` 执行：

```bash
"$VENV_DIR/bin/python" manage.py migrate --noinput
```

若目标库是现存的原 Laravel 生产库，Django 会因为找不到自己的迁移记录表而尝试重新执行 `0001_initial`，第一条 `CREATE TABLE users` 就会以 "relation already exists" 失败。

同时 `0004` 会对 35 个列执行 `ALTER COLUMN SET DEFAULT`，这是对生产表的真实写操作。

**风险**：这是迁移场景下最典型的失败点。要么加 `--fake-initial`（仅能跳过首次建表，无法跳过 0004 的 ALTER），要么先在生产库上按迁移顺序完整演练一遍。

### 5.2 高：数据正确性

#### 缺陷 2｜`default=' '` 被加在唯一约束列上，该默认值实际不可用

`0004` 给三个**唯一列**加了 `default=' '`：

| 表 | 列 | 约束 |
| --- | --- | --- |
| `users` | `username` | `unique=True` |
| `person` | `card` | `unique=True`（身份证） |
| `personal_access_tokens` | `token` | `unique=True` |

任何一个代码路径若漏传该字段，第一行会以空格入库成功，**第二行立即触发唯一约束冲突**。`person.card` 是身份证号，一旦发生会直接导致人员建档失败。

该 workaround 的原始动机是兼容 GaussDB（PostgreSQL 9.2.4 兼容模式）把空串当 NULL 处理的行为。但在标准 PostgreSQL 上，它把"漏填"从**显式报错**变成了**静默写入一个空格**，掩盖数据缺失。二者不可兼得，需要按目标引擎二选一。

#### 缺陷 3｜审计日志把匿名事件记到 1 号用户名下

`apps/core/services.py:72`：

```python
Logs.objects.create(user_id=user.id if user else 1, type=action_type, ...)
```

`user` 为空时回落到字面量 `1`。触发该路径的场景包括登出（`views.py:273`）和 OSS 上传凭证发放失败（`views.py:950`）。

**后果**：这些失败/匿名事件在审计表中全部归属到 1 号用户（管理员）。审计轨迹的可信度受损，事后追责时会产生误导。

#### 缺陷 4｜`report.group` 同一列混存两种格式

同一逻辑分组在数据库中有两种表示，且被不同接口分别写入和查询：

| 格式 | 示例 | 使用点 |
| --- | --- | --- |
| 中文名 | `group="大学组"` | `views.py:715`（省级统计） |
| 数字串 | `group=str(0..3)` | `views.py:718-723`（市级/校级统计） |

导出时还要靠一张映射表把中文名转成 1..3 来生成报送编码（`apps/api/export_services.py:63-77`）。

**后果**：按 `group` 做等值筛选或计数时，两种形态会导致**静默漏统计**——查得到中文的查不到数字的，反之亦然。数字形态的语义为：0=中小学组、1=大学组、2=中小学教师组、3=高校教师组。

### 5.3 中：结构性隐患

#### 缺陷 5｜关联列宽度 int4/int8 混用

所有主键都是 `bigserial`（int8），但指向它们的关联列宽度不统一：

| 列 | 类型 | 目标主键 | 是否匹配 |
| --- | --- | --- | --- |
| `report.user_id` | `integer` (int4) | `users.id` bigserial | 否 |
| `report_person.report_id` | `integer` | `report.id` bigserial | 否 |
| `report_person.person_id` | `integer` | `person.id` bigserial | 否 |
| `crew.live_report_id` | `integer` | `live_report.id` bigserial | 否 |
| `leader.live_report_id` | `integer` | `live_report.id` bigserial | 否 |
| `ticket_subscribe.ticket_id` | `integer` | `ticket.id` bigserial | 否 |
| `logs.user_id` | `bigint` | `users.id` bigserial | 是 |
| `live_report.report_id` | `bigint` | `report.id` bigserial | 是 |
| `personal_access_tokens.tokenable_id` | `bigint` | `users.id` bigserial | 是 |

这是从 Laravel 端原样照抄的结果。21 亿以内安全，PostgreSQL 也不会静默截断（会报错），因此不紧急；但**同一语义的字段宽度不一致**（如 `logs.user_id` 是 bigint 而 `report.user_id` 是 int4）本身说明缺少统一规范，长期是隐患。

#### 缺陷 6｜`users.parent_id` 用 0 当"无上级"哨兵，与该列的 NULL 语义冲突

管理员创建用户时写死 `values["parent_id"] = 0`（`views.py:516`），而该列本身是可空的。

**后果**：同一列混用 `NULL` 和 `0` 两种"空"表示。由于外键无约束，`0` 是一个指向不存在记录的**悬空引用**。任何 `parent_id__isnull=True` 的统计都会漏掉这批记录。

#### 缺陷 7｜`live_report.report_id` 是死链接

该列被写入，但全部代码中**没有任何读取点**（穷举 `.report_id` 的结果只有指向 `ReportPerson.report_id` 的 `export_services.py:112`）。

**后果**：现场报名表与节目报名表之间的关联在 Django 侧实际是装饰性的。任何依赖该链路的查询或报表都无法工作。

#### 缺陷 8｜JSON 字段物理上是 text，没有 JSONB

4 个 JSON 字段（`report.dinner_reservation`、`scan_files.files`、`recommend.file`、`live_report.files`）由自定义的 `LegacyJSONField`（`models.py:20`）承载，它是 **`TextField` 的子类**。

| 影响 | 说明 |
| --- | --- |
| 无 JSON 路径查询 | 不能写 `files->0->>'id'` |
| 无 GIN 索引 | JSON 内容无法高效检索 |
| 应用层解析 | 所有读写都经过 Python 的 `json.loads/dumps` |

这是为规避 PostgreSQL 9.2.4 / GaussDB 的 JSONB 支持不确定性而做的保守选择，方向合理，但代价是上述查询能力永久缺失。

#### 缺陷 9｜软删除支持不完整

| 表 | 有 `deleted_at` | 有软删管理器 |
| --- | --- | --- |
| `users` | 是 | 是（`UserManager`） |
| `report` | 是 | 是（`SoftDeleteManager`） |
| `report_person` | 是 | 是 |
| `statistics` | 是 | **否** |
| `person` | **否** | — |
| `students` | 否 | — |
| `crew` / `leader` | 否 | — |

两处需要关注：

- `statistics` 有软删字段却没有管理器，写法不一致；
- **`person` 完全没有删除标记**——人员行永不删除，而 `person.card` 是唯一约束。这意味着一个已离队/作废的身份证号会**永久占用**该约束，无法重新建档。这是业务逻辑层面的实际影响，不只是风格问题。

#### 缺陷 10｜`password_resets` 表结构与原库不兼容

原 Laravel 的 `password_resets` 表**没有主键**，Django 模型强行补了 `id bigserial`（`models.py:444-451`），且 `0002` 将其设为 `managed=True`。

**后果**：向已有数据库附加时，该表会缺失 `id` 列，Django 的任何写入都会失败。

### 5.4 提示：文档与代码不符

| 文档说法 | 实际情况 |
| --- | --- |
| `MIGRATION_GAPS.md` 称 `users.parent_id` "在原迁移中缺失" | 现已建模并建立了 FK 关系，文档未同步 |
| `MIGRATION_GAPS.md` 列出 `report.origin/territory/group_type` 为"运行时引用但迁移缺失" | 属实。代码中用 `getattr/hasattr` 兜底（`views.py:734`、`792-794`），即**这些列在当前 schema 中确实不存在**，相关功能静默降级为 0 |
| `DATABASE_MAPPING.md` 未提及 `statistics` 有 `deleted_at` 无管理器 | 见缺陷 9 |
| `DATABASE_MAPPING.md` 称 `students`/`statistics` 是"被源码引用但无迁移" | 实际是**零业务引用**的空壳，只注册在 `admin.py` |

## 七、建议处置顺序

按"投入产出比"排序：

1. **修复部署流程**（缺陷 1）——在 `deploy.sh` 的 `migrate` 前补 `--fake-initial` 判断，或改为先在影子库演练。这是唯一会直接导致上线失败的问题。
2. **处理唯一列上的 `default=' '`**（缺陷 2）——确认目标引擎是否为 GaussDB，据此决定是移除默认值、还是仅在非唯一列保留、还是改用触发器。涉及 `person.card`，优先级最高。
3. **修正审计日志归属**（缺陷 3）——把回落值改为 `NULL` 或专门的系统账号 ID，避免污染管理员的操作记录。
4. **统一 `report.group` 格式**（缺陷 4）——需要一次数据订正（把中文名批量转成数字串，或反之）加代码统一，属于需要业务确认的变更。
5. **评估 `person` 的软删除与身份证占位问题**（缺陷 9）——涉及业务规则，需要数据所有者确认。
6. **补齐 `live_report.report_id` 的读取或明确废弃**（缺陷 7）。
7. 其余结构性隐患（缺陷 5、6、8、10）可随其他改动一并处理。
